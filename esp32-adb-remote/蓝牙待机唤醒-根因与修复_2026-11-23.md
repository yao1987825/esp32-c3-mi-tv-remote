## 一句话答案

**原装遥控器能唤醒电视，是因为它的广播包里有一个我们一直在漏看的字段：
AD type `0xFE`，内容是「电视自己蓝牙地址的后 3 字节（逆序）」。**

待机的电视在自己的广播里看到这个点名信，就知道「这条广播是发给我的」，
于是唤醒自己并主动连回遥控器。

我们的克隆之前**从来没有发过**这个字段 —— 不是发错了，是压根不知道它的存在。

---

## 为什么之前一直找不到

我们自己的嗅探器（板子上的 `ble_mi_remote` 组件）只打印一张**固定**的 AD type 表：

```cpp
static const uint16_t kAdTypes[] = {
    0x01, 0x02, 0x03, 0x04, 0x05, 0x06, 0x07, 0x08,
    0x09, 0x0A, 0x16, 0x20, 0x21, 0x22, 0xFF
};
```

**`0x0D` 和 `0xFE` 都不在里面。** 那些字节一直都在空中，只是从来没被打印出来
（`%TEMP%\sniff_asleep.log` 里那条 `MI RC` 记录因此少了两段）。

嗅探器现已改成**同时打印完整原始包**（`raw=[...]`），并把 `0x0D`/`0xFE` 加进了解析表。

2025-09 由 MiPower 作者点名「我解决了」）

它广播的原始字节：

```
02 01 05              Flags
03 FF 00 01           厂商数据 company id 0x0000
06 08 4D 49 20 52 43  短名 "MI RC"
03 02 12 18           16bit UUID 0x1812 (HID)，AD type 0x02 = 不完整列表
04 0D 04 05 00        设备类别字段
02 0A 00              TX power 0 dBm
04 FE 28 48 19        ★ 小米唤醒字段 = 电视自己地址的后 3 字节（逆序）
```

README 原话：*「遥控器按电源后发一条广播，最后一个字段（type 0xFE）
装着**电视自己地址的后 3 字节**；芯片看到这个就唤醒电视。」*

它测的是 MT7668（联发科），我们是 qca9377（高通），所以机制**不保证**完全一样——
但照抄过来，在这台电视上**实测有效**。

### 3. 求证：**在这台电视上实测**到的原装遥控器广播包

2026-11-23 深夜，用修好的嗅探器（打印完整原始包 + 解析 `0x0D`）在这台电视旁
抓到的原装「小米蓝牙语音遥控器」（`D4:B8:FF:7D:AD:6D`）广播：

```
SNIFF D4:B8:FF:7D:AD:6D rssi=-32 advType=0x00 name='MI RC' mfg=[00 00]
  ad=[T01:05 | T03:12 18 | T08:4D 49 20 52 43 | T09:4D 49 20 52 43 | T0A:00 | T0D:04 05 00 | TFF:00 00 ]
  raw=[02010503FF000006084D4920524303031218040D040500020A00]
```

逐段拆开：

| 段 | 原样 | 含义 |
|---|---|---|
| `02 01 05` | Flags | LE 可被发现 + 不支持 BR/EDR |
| `03 FF 00 00` | 厂商数据 | company `0x0000`，payload **`00`** |
| `06 08 4D 49 20 52 43` | 短名 | `"MI RC"` |
| `03 03 12 18` | 16bit UUID | `0x1812`（HID），AD type **`0x03`** 完整列表 |
| `04 0D 04 05 00` | 设备类别 | `0x0D` 字段，值 `04 05 00` |
| `02 0A 00` | TX power | 0 dBm |

**两个当场被证实的事实：**

1. **原装遥控器确实带 `0x0D` 设备类别字段**（`04 05 00`）—— 之前我们的嗅探器
   根本不打印这个 AD type，所以从来没人知道它存在。我们广播包里的
   `04 0D 04 05 00` 现在是**逐字节对上了**。
2. **这是它的「常态」包，里面没有 `0xFE`**。也就是说 `0xFE` 是**按键唤醒时才
   临时发**的字段，不是常驻字段。

把两边摆一起看，答案就很清楚了：

| 字段 | 原装遥控器（常态） | 原装遥控器（唤醒时，据参考实现） | 我们板子 `mi_wake` |
|---|---|---|---|
| 厂商数据 payload | `00` | `01` | `01` ✅ |
| UUID 列表 AD type | `03`（完整） | `02`（不完整） | `02` ✅ |
| `0x0D` 设备类别 | `04 05 00` | `04 05 00` | `04 05 00` ✅ |
| **`0xFE` 电视地址** | 无 | **有** | **有** ✅ |

**我们板子发的是原装遥控器「唤醒态」的包，逐字节一致。**

> 所以「原装遥控器为什么行」的完整答案是：
> 它按电源键时，除了发 HID 键，还会临时广播一个**点名信** ——
> `0xFE` 字段里装着**电视自己地址的后 3 字节（逆序）**。
> 待机的电视在自己的扫描窗口里听到这条广播，一比对「这不就是我的地址吗」，
> 就知道「这条是发给我的」，于是唤醒自己并主动连回来。
>
> 我们之前**不是发错了字段，是压根不知道有这个字段**。
> 而 `0x0D` 这个字段又证明了一件事：原装的包结构非常具体，
> 少一个字段都不行（Android 6 的电视端对遥控器广播的校验比想象中严）。

## 四条后续结论（必须记住，否则测试结论全是假的）

### 结论 A：广播必须**连续**发，占空比广播会被待机扫描漏掉

最初唤醒包是按 **1.28 s 开 / 1.3 s 关** 的占空比发的（ESPHome 默认的
`advertising` 周期行为）。电视**有**机会扫到，但经常整轮都错过 —— 表现为
「偶尔能唤醒，更多时候唤不醒」，非常像随机故障。

改成**连续快广播**（间隔 32/48，即 20~30 ms）之后，唤醒稳定复现。

原因：待机的电视用的是**低占空比（low duty cycle）扫描**，只在扫描窗口开启的
那一点点时间里听。20~30 ms 的广播间隔意味着几乎每个扫描窗口里都有一帧，
而 1.28 s 的间隔会让整个扫描窗口常常一帧都听不到。

> 这条同时解释了「为什么原装遥控器总是能唤醒」：它按的是用户按键，
> 只要电视扫到**一帧**就够了，遥控器不需要连续发很久。
> 但对我们来说，连续发才稳。

广播实现上就是把广播间隔统一到 **32/48**，并且**取消开/关切换**
（原来的 `powerAdvertStart` / `powerAdvertStop` 逻辑改成只发一次、不再定时关）。

### 结论 B：测试脚本必须等 `onDisconnect` 处理完，再按第二次

板子的 `_connected` 标志由 `onConnect()` / `onDisconnect()` 维护。电视进待机后
GATT 链路会断开，但板子**过一会儿**才收到回调并把 `_connected` 置为 false。

如果测试脚本在「ADB 一断」就立刻按第二次电源键，此时板子仍认为**自己连着**，
于是走 `is_connected() == true` 分支，把电源键**直接塞进那具正在睡着的电视** ——
电视根本没听见，只收到了唤醒广播；或者反过来，电视被唤醒后收到补发的电源键
又立刻睡回去。**两种情况都会让测试得出「唤醒失败」的错误结论。**

所以 `tools/test_wake_packet.py` 现在在「进待机」之后会 `time.sleep(12)`，
等板子处理完 `onDisconnect` 再按第二次。

**判断依据**：串口日志里应先出现

```
pressSpecial: key=... connected=YES      <- 第一次按键（电视还醒着）
...
onDisconnect ...                           <- 板子收到断链
pressSpecial: key=... connected=NO       <- 第二次按键（这次只发广播，不排队）
```

如果第二次按键日志里还是 `connected=YES`，那这次测试的结果**不可信**。

### 结论 C：**常态广播和唤醒广播必须是两个包**

这条是 2026-11-24 用户反馈「**为什么我没有按开机，电视自动开机**」才暴露出来的，
也是这一晚最后一个、也是最隐蔽的一个坑。

我们之前把**唤醒包直接当成了常态广播包**（`advert_style: mi_wake` 在 `setup()`
里就把 ADV 数据设成了带 `0xFE` 的那一份）。而 `0xFE` 字段里装着**电视自己的
地址** —— 于是电视每收到一帧广播都在被点名，**没人按遥控器它也会自己开机**。

**原装遥控器不是这么做的**。2026-11-23 在这台电视上实测抓到的它的常态包：

```
raw=[02010503FF000006084D4920524303031218040D040500020A00]
     Flags | mfg 00 00 | 短名 "MI RC" | UUID(type 03) | 0x0D | TX
```

**没有 `0xFE`**。参考实现的 README 也写得很清楚：

> on `wake()` sends that same advertisement for **3 seconds**.
> The real remote keeps working: **the ESP32 only speaks when asked.**

所以正确的分工是：

| | 什么时候发 | 内容 |
|---|---|---|
| **常态包** | 一直发（20/30 ms 连续） | 同结构，但**没有 `0xFE`**、厂商数据字节 `0x00`、UUID 列表 type `0x03` |
| **唤醒包** | **只在按键时**发 30 秒 | 带 `0xFE`、厂商数据字节 `0x01`、UUID 列表 type `0x02`（与参考实现逐字节一致） |

配套的两条规则：

1. **电视在线时不要发唤醒包**。在线说明电视是醒的，键直接过去就够。
   尤其电源键：在线时发唤醒包 = 电视被关掉后又被我们自己的 `0xFE` 帧立刻唤醒。
2. **电视连回来后立刻停发唤醒包**。它都醒了，没必要继续点名。

> **教训**：这类「广播包内容」的问题，必须分清**常态**和**按键态**两个包。
> 我们之前只顾着「让电视认得我们的广播」，没想到 `0xFE` 是一封**点名信** ——
> 常发等于一直点名。

**最终的产品形态（v1.1.0）**：

| 配置项 | 默认 | 作用 |
|---|---|---|
| `advert_style: mi_idle` | ✅ | 常态广播 = 不带 `0xFE` 的常态包 → **电视不会自己醒** |
| `wake_on_press: true` | ✅ | 电视待机时，按板子任意键能唤醒它（和原装遥控器一样） |

所以用户的两条开机路径都成立：**用原装遥控器开**、**用板子开**，
而「没人按键电视自己开」这个毛病没了。

回归测试：`tools/test_no_self_wake.py`
（电视进待机后什么都不按 N 分钟，电视不能自己醒；最后按一次作对照组必须能唤醒）。

### 结论 D：检测「电视是否醒了」必须重新 `adb connect`

这条最容易把人带沟里——它让**一次已经成功的唤醒**被判定成失败。

电视从待机唤醒后，整个 WiFi/ADB 会话是**重建**的：ADB 客户端列表里那个
`192.168.6.209:5555` 变成死条目，必须重新 `adb connect` 才能用。
而 `adb -s 192.168.6.209:5555 shell ...` 对着一个死条目只会报
`device not found`，**永远**查不到电视。

实测翻车现场：

```
[ 46.4s] onConnect: peer=C8:28:32:62:77:AA    ← 电视自己连回来了，唤醒其实成功
[ 86.4s] onDisconnect: reason=0x222             ← 40s 无响应，链路层 supervision timeout
>>> 超时，电视仍不可达                            ← ❌ 脚本的误判
```

手动跑一次 `adb connect` 就发现电视是活的（`TV_ALIVE`）。

所以 `tools/test_wake_packet.py` 现在：
- `adb_alive(connect=True)`：先 `adb connect` 再 `shell`
- `wait_dead()` 判定电视进待机后，先 `adb disconnect` 清掉死会话
- 唤醒成功后额外读一次 `dumpsys power | grep mWakefulness`，
  确认屏幕是**真的亮了**，而不只是 ADB 通

> ⚠ **还有第二个坑（同一个原因）**：电视唤醒后，adb server 里那条
> `192.168.6.209:5555` 会变成 **`offline`** 的陈旧条目。此时再跑
> `adb connect`，adb 会直接回 **`already connected`** 而**不再真正建连**，
> 紧接着 `adb shell` 就报 `device offline` —— 看起来像"电视又睡了"，
> 其实是**假象**。
>
> 正确姿势是**先 `adb disconnect` 再 `adb connect`**。
> 用这个姿势复查时，电视其实一直醒着（`mWakefulness=Awake` 连续多次），
> 根本没有自己睡回去。
>
> `tools/watch_after_wake.py` 就是按这个姿势写的，可以用来盯"电视会不会
> 自己又睡回去"。

> 顺带说明 `reason=0x222`：那是链路层的 supervision timeout ——
> 电视连回来了但没真正醒（或者又睡了），所以 40 秒没响应。
> **BLE 层连上 ≠ 电视醒了**，这条也是判断唤醒成功的必要区分。

## 电视侧已知事实（2026-11-23 实测）

- 电视：`MiTV4-ANSM0`，Android 6.0.1，蓝牙芯片 `qca9377`（高通）
- 电视 BLE 地址：`C8:28:32:62:77:AA`（random static）
- 原装遥控器：`D4:B8:FF:7D:AD:6D`（random static）
- 板子：`9C:96:D5:B0:C2:7E`（public）—— **待机唤醒不需要改地址**
- 电视**没有** `persist.bluetooth.wakeuprcaddr` 属性（那是联发科方案的）
- 电视待机时仍在广播 MiBeacon（company 0x038F / service 0xFE95）→ **蓝牙主机是活的**
- 电视**不回 ICMP**，只能用 ADB 5555 判断死活
- 电视的待机扫描是**周期性**的：唤醒包发出后 **17~36 秒**才连回来
- 电视唤醒后 **WiFi/ADB 会话整个重建**，ADB 客户端必须重新 `adb connect`
- 电视蓝牙列表**只显示已缓存过的名字** → 名字保持 `MI Remote`

## 日常怎么用

电源键现在是**双向**的（亮屏 ↔ 待机）：

| 电视状态 | 按电源键 | 结果 |
|---|---|---|
| 亮屏 | 发 HID 电源键 | 电视进**关屏待机**（BLE 保持，不断电） |
| 待机（BLE 还连着） | 发 HID 电源键 + 唤醒广播 | 电视**重新亮屏**（实测 ~36 秒） |
| 彻底关机（拔电才能恢复） | 任何 BLE 手段都唤不醒 | — |

调用方式（ESPHome web_server / HA 自动化都走这个实体）：

```
POST http://192.168.6.101/ble-mi-remote-Power
```

或者直接跑 `python tools/tv_remote.py Power`。

> ⚠ 电视**不要**用 `adb shell input keyevent 223` 进待机 ——
> 实测那会让电视进入「拔电源才能恢复」的死状态。用遥控器的 HID 电源键短按进 standby。

## 还没做的两件事（可选）

1. **抓原装遥控器的「唤醒态」包**（带 `0xFE` 的那一个）。
   常态包已经抓到了（见上），唤醒包只在**电视待机时**按电源键的那一瞬间发，
   上一次窗口没赶上。做法：电视进待机 → `python tools/sniff_loop.py 300` →
   按一下原装遥控器电源键。纯属求证，功能已经通了。
2. **唤醒后自动把电源键发给电视**：现在电源键只做「唤醒」，唤醒后屏幕亮着。
   如果想让「按一次电源键 = 开机、再按一次 = 关机」这种语义成立，
   需要在唤醒成功后补发一个电源键 —— 但要小心别把刚唤醒的电视又关掉。
